- [x] Resumable/crash-resilient runs (2026-08-04, ROADMAP.md Phase 3/v0.4.0 item, maintainer: "keep on working on roadmap entries, overnight... git commit them"). A killed or crashed `ruchat` process previously lost all progress, restarting from `Stage::Scope` every time — no way to recover a long multi-round run's already-completed work.
  - New `core/orchestrator/checkpoint.rs::Checkpoint`: a small, explicit subset of `Context` (`goal`/`turns`/`round`/`pending_patches`/`trace_index`) plus the `Stage` just transitioned into, serialized to `ruchat_checkpoint.json` after every non-terminal stage transition in `run_stage_machine`'s main loop (`Stage::Done`/`Stage::Escalate` both `break` before the save point is reached, so this only ever fires for a genuine continuing transition). `Turn`/`TurnKind`/`PendingPatch`/`Stage` all gained `Serialize`/`Deserialize` derives for this — plain data, no invariants a round-trip could violate. Deliberately NOT the whole `Context`: `output` (transient scratch, overwritten by the next role call regardless) and `context_config` (already re-derived fresh from `db_config.json` at the top of `run_stage_machine` for both fresh and resumed runs) don't need to survive.
  - `Checkpoint::clear()` deletes the file the moment `Stage::Done` or `Stage::Escalate` is reached — both are the stage machine *deciding* to stop, a recorded outcome, not a crash; `--resume` is specifically for surviving an *unexpected* interruption, so a run that finished on its own (successfully or not) has nothing left to resume. `save`/`clear` are both best-effort (a checkpoint I/O failure is logged, never propagated — a diagnostic nicety failing must never abort an otherwise-healthy run), while `load` (used only by `--resume` itself) surfaces a clear error on a missing or corrupt checkpoint rather than silently starting fresh, since silently discarding what looked like resumable state would be a worse surprise.
  - New `ruchat pipe --resume` flag (`conflicts_with_all` the positional prompt and `--debug-sequence` — mutually exclusive concepts, not two things to combine): reloads the checkpoint and continues from the last completed stage instead of `Context::new`/`Stage::Scope`, and crucially preserves `trace_index` (not re-allocated) so a resumed run keeps appending to the *same* trace file instead of starting a new one that would lose the pre-crash history. `--resume` still needs the same `--team-model`/`--agentic` the original interrupted run used — the checkpoint recovers conversation state, not which agent roles/models to reconstruct; explicitly rejected with a clear error if `--resume` is combined with no Architect/Worker config at all (the non-agentic OneShot path has no `Context`/`Stage` machine, nothing to resume). `AgentPipeline::Orchestrator`/`Orchestrator::run_task_stream`/`debug_stage_machine`'s existing `DebugBreakpoints` parameter both gained a sibling `resume: bool` threaded the same way; `ruchat manager run` passes `resume: false` (Team presets don't get resume support in this pass — deferred, matches the same scope decision already made for `--chat-provider` there).
  - Caught and fixed a real, self-introduced test-flakiness bug while writing this: the first version of `checkpoint.rs`'s tests used `std::env::set_current_dir` to isolate each test's checkpoint file in a temp directory, guarded by a mutex — but the mutex only serialized the checkpoint tests *against each other*, not against every *other* concurrently-running test in a different thread that also depends on the real working directory (`std::env::set_current_dir` is process-global, not per-thread). Caused two unrelated, real `git`-dependent tests (`apply_patch_rejects_target_outside_declared_scope`, `apply_patch_shows_real_file_content_when_context_does_not_match`) to fail intermittently with "Unable to read current working directory." Fixed by parameterizing `Checkpoint::save`/`load`/`clear` with an explicit `path: &Path` instead of an implicit CWD-relative constant — tests now point at a tempdir path directly, no global process state touched at all. Confirmed fixed by running the full suite three times in a row with zero failures (was intermittent before, so a single clean run wouldn't have been convincing).
